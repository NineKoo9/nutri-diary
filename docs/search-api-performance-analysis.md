# Nutri-Diary 검색 API 성능 분석 보고서

> 작성일: 2026-03-26
> 대상 서비스: Nutri-Diary (다이어트 음식 기록/공유 서비스)
> 기술 스택: Spring Boot 3.3.2 + Elasticsearch + MySQL (Spring Data JDBC) + HikariCP

## 1. 검색 API 사용 빈도 분석

### 서비스 특성

다이어트 음식 기록/공유 서비스에서 검색은 **핵심 기능**이다.

### 사용자 행동 패턴 (DAU 10,000명 기준)

| 시나리오 | 설명 | 일 평균 검색 횟수/인 |
|---------|------|-------------------|
| 식사 기록 시 제품 검색 | 하루 3끼 + 간식 1~2회 | 4~5회 |
| 자동완성/타이핑 중 검색 | 한 번 검색에 3~5회 API 호출 (keystroke debounce 적용 시) | 12~25회 |
| 스토어 제품 탐색 | 상품 브라우징, 페이지네이션 | 2~3회 |
| 리뷰/태그 기반 탐색 | 다이어트 태그로 필터링 | 1~2회 |

### 일일 총 검색 API 호출량 추정

```
보수적 추정: 10,000명 × 15회/일 = 150,000 req/day
현실적 추정: 10,000명 × 25회/일 = 250,000 req/day
공격적 추정: 10,000명 × 40회/일 = 400,000 req/day
```

### 시간대별 트래픽 분포 (식사 기록 서비스 특성)

```
시간대        비율      RPS (현실적 기준 250K/day)
─────────────────────────────────────────────────
07:00-09:00   15%       ~5.2 RPS   (아침 식사 기록)
11:30-13:30   25%       ~8.7 RPS   (점심 식사 기록) ← 피크 1
14:00-17:00   10%       ~1.7 RPS   (간식/탐색)
18:00-20:00   30%       ~10.4 RPS  (저녁 식사 기록) ← 피크 2
20:00-23:00   15%       ~3.5 RPS   (야식/다음날 준비)
기타           5%       ~0.4 RPS
```

**피크 시간대 보정 (버스트 트래픽):**
- 평균 피크 RPS: ~10.4
- **순간 버스트 (피크의 3~5배):** 30~50 RPS
- 이벤트/프로모션 시: 최대 100 RPS까지 고려

## 2. 목표 응답 속도 (Latency Target)

### 업계 표준 벤치마크

| 구분 | P50 (중앙값) | P95 | P99 | 비고 |
|------|------------|-----|-----|------|
| 자동완성/Suggest | < 50ms | < 100ms | < 200ms | 타이핑 중 실시간 피드백 |
| 전체 검색 결과 | < 100ms | < 200ms | < 500ms | 결과 리스트 표현 |
| 필터/정렬 포함 검색 | < 150ms | < 300ms | < 500ms | 태그+검색 조합 |
| 페이지네이션 | < 100ms | < 200ms | < 300ms | 다음 페이지 로드 |

### Nutri-Diary에 적합한 목표치

현재 구조(`ProductSearchService` → Elasticsearch → MySQL 조인)를 고려하면:

```
[클라이언트] → [API 서버] → [Elasticsearch 검색] → [MySQL 보강 조회] → [응답]
                  ↓              ↓                      ↓
               ~5ms           ~20-50ms              ~30-80ms
```

**현재 아키텍처 기준 현실적 목표:**

| 지표 | 목표 | 근거 |
|------|------|------|
| **P50** | **< 100ms** | ES 검색 + MySQL 리뷰/태그 조회 합산 |
| **P95** | **< 300ms** | 네트워크 지터, GC pause 등 고려 |
| **P99** | **< 500ms** | Cold cache, connection pool 대기 포함 |
| **P99.9** | **< 1000ms** | 극단적 상황 (ES shard relocation 등) |
| **Error Rate** | **< 0.1%** | 검색 실패 시 사용자 이탈 높음 |

> **참고:** 현재 `ProductSearchService`에서 ES 검색 후 `reviewRepository`와 `productDietTagRepository`를 추가 조회하는 구조이므로, **네트워크 라운드트립이 최소 2~3번** 발생한다. 이 부분이 병목이 될 수 있다.

## 3. DAU 10,000명 기준 필요 성능 스펙

### 3-1. 서버 리소스

```
현재 설정:
- Tomcat max threads: 60
- HikariCP max pool size: 40

피크 시 동시 요청 수: ~50 concurrent requests (버스트 기준)
```

**Tomcat 스레드 60개 검증:**
```
필요 스레드 수 = RPS × 평균 응답시간(초)
= 50 RPS × 0.15s (150ms)
= 7.5 스레드 (평균)

버스트 시: 100 RPS × 0.3s = 30 스레드

→ 60 스레드면 DAU 10,000명 수준에서는 충분
```

**HikariCP 40개 검증:**
```
필요 커넥션 = 동시 DB 쿼리 수 × 쿼리 평균 시간
= 30 concurrent × 0.05s (50ms)
= 1.5 active connections (평균)

버스트 시: 60 concurrent × 0.08s = 4.8 active connections

→ 40개는 DAU 10,000명에서는 과잉. 15~20개면 충분
   (단, 비동기 ES 동기화 작업이 커넥션을 점유할 수 있으므로 여유분 필요)
```

### 3-2. Elasticsearch 성능 요구사항

| 항목 | 요구 스펙 | 비고 |
|------|----------|------|
| 인덱스 크기 | < 1GB (제품 수 100만개 이하) | 식품 데이터 특성상 |
| 샤드 수 | 1~2개 | 소규모 인덱스 |
| 레플리카 | 1개 | 가용성 확보 |
| 검색 latency | < 50ms (ES 단독) | `findByProductName` 기준 |
| Indexing throughput | < 10 docs/sec | 신규 제품 등록 빈도 |

### 3-3. 처리량(Throughput) 목표

```
일반 시간대:  3~5 RPS, 응답시간 < 100ms
피크 시간대: 10~15 RPS, 응답시간 < 200ms
버스트:      30~50 RPS, 응답시간 < 500ms
극한:       ~100 RPS, 에러율 < 1%
```

### 3-4. 가용성(Availability)

| 지표 | 목표 | 허용 다운타임/월 |
|------|------|----------------|
| 99.9% | 적절 | ~43분/월 |
| 99.5% | 최소 | ~3.6시간/월 |

## 4. 현업에서 API 스펙 정할 때 추가 고려사항

### 4-1. SLI/SLO/SLA 정의

```
SLI (Service Level Indicator): 실제 측정하는 지표
  → 응답시간, 에러율, 처리량

SLO (Service Level Objective): 내부 목표
  → "검색 API P95 < 300ms, 에러율 < 0.1%"

SLA (Service Level Agreement): 외부 계약 (B2B인 경우)
  → "월 가용성 99.9% 미달 시 크레딧 환불"
```

### 4-2. Rate Limiting / Throttling

```yaml
# 현업 예시
rate_limit:
  per_user: 60 req/min      # 사용자당 분당 60회
  per_ip: 120 req/min       # IP당 분당 120회
  global: 1000 req/sec      # 전체 시스템
  search_specific: 30 req/min  # 검색은 더 비싸므로 별도 제한
```

현재 Nutri-Diary에는 Rate Limiting이 없는 상태이다. DAU가 늘어나면 반드시 필요하다.

### 4-3. 페이지네이션 전략

현재 `Pageable`을 사용 중인데, 현업에서는:

| 방식 | 장점 | 단점 | 적합한 경우 |
|------|------|------|-----------|
| Offset-based (현재) | 구현 간단, 특정 페이지 이동 | deep pagination 성능 저하 | 결과 < 10,000건 |
| Cursor-based | 일관성, 대규모에 적합 | 특정 페이지 점프 불가 | 무한 스크롤, 대규모 |
| Search After (ES) | ES 최적화, 깊은 페이지 가능 | 구현 복잡 | ES 직접 사용 시 |

### 4-4. 캐싱 전략

현재 캐싱 레이어가 없다. 고려할 사항:

```
1. 인기 검색어 캐싱 (Redis, TTL: 5~10분)
   → "닭가슴살", "고구마" 등 반복 검색어 캐싱
   → 히트율 예상: 30~50% (식품 검색 특성상 인기 키워드 집중)

2. 검색 결과 캐싱
   → 동일 쿼리+페이지 결과를 Redis에 캐싱
   → TTL: 1~5분 (새 제품 등록 반영 지연 허용 범위)

3. 리뷰 수/태그 캐싱
   → 현재 매 검색마다 MySQL 조회하는 리뷰 수, 태그 정보
   → Local cache (Caffeine) 또는 Redis, TTL: 10~30분
```

### 4-5. 검색 품질 지표 (현업 필수)

| 지표 | 설명 | 측정 방법 |
|------|------|----------|
| **Zero Result Rate** | 검색 결과 0건 비율 | < 5% 목표 |
| **Click-Through Rate** | 검색 후 제품 클릭 비율 | > 40% 목표 |
| **Time to First Click** | 검색~첫 클릭까지 시간 | < 5초 목표 |
| **Search Abandonment** | 검색 후 이탈 비율 | < 20% 목표 |
| **Reformulation Rate** | 재검색 비율 (낮을수록 좋음) | < 30% 목표 |

### 4-6. 장애 대응 (Graceful Degradation)

```
ES 장애 시 → MySQL LIKE 검색으로 fallback (현재 미구현)
MySQL 장애 시 → 검색은 가능하되 리뷰/태그 없이 반환
전체 장애 시 → 정적 인기 제품 목록 반환 (캐시)
```

### 4-7. 보안 고려사항

| 항목 | 현재 상태 | 권장 |
|------|----------|------|
| SQL Injection | Spring Data JDBC 파라미터 바인딩으로 안전 | OK |
| ES Injection | `findByProductName` 메서드 쿼리로 안전 | OK |
| 검색어 길이 제한 | 미구현 | max 100자 권장 |
| 특수문자 필터링 | 미구현 | ES 쿼리 예약어 이스케이프 필요 |
| 로깅/감사 | 미구현 | 검색어 로그 (개인정보 주의) |

### 4-8. 국제화/확장성

```
현재: 한국어 제품명 검색 (productName)
고려:
  - 한국어 형태소 분석기 (nori analyzer) 적용 여부
  - 초성 검색 (ㄷㄱㅅㅅ → 닭가슴살)
  - 오타 교정 (fuzzy search)
  - 동의어 사전 (닭가슴살 = 닭가슴 = 치킨브레스트)
```

### 4-9. API 버저닝 & 하위호환성

```
현재: /product?search=...
권장: /v1/product/search?q=... (명시적 버전, 검색 전용 엔드포인트)

응답 포맷에 포함할 메타데이터:
{
  "data": [...],
  "meta": {
    "total": 1234,
    "page": 1,
    "size": 20,
    "took_ms": 45,
    "query": "닭가슴살"
  }
}
```

## 5. 종합 권장 사항 (우선순위순)

| 순위 | 항목 | 현재 상태 | 영향도 |
|------|------|----------|--------|
| 1 | **리뷰/태그 조회 최적화** | 매 검색마다 N+1 쿼리 발생 가능 | 응답속도 직접 영향 |
| 2 | **인기 검색어 캐싱 (Redis)** | 캐시 없음 | ES 부하 30~50% 감소 |
| 3 | **ES fallback 구현** | ES 장애 시 전체 검색 불가 | 가용성 |
| 4 | **Rate Limiting** | 없음 | 남용 방지 |
| 5 | **검색 품질 메트릭 수집** | 없음 | 서비스 개선 기반 |
| 6 | **한국어 형태소 분석기** | 기본 텍스트 매칭 | 검색 품질 |

DAU 10,000명 수준에서는 현재 인프라(Tomcat 60 threads, HikariCP 40)로 **트래픽 자체는 충분히 처리** 가능하다. 병목은 트래픽 양이 아니라 **검색 품질**과 **ES→MySQL 다중 조회 latency**에서 올 가능성이 높다.

# Product 100만건 / Review 1,000만건 기준 DAU 역추정 분석

## 1. 핵심 가정 수립

### Product 데이터 특성

식품 제품 데이터는 **사용자가 직접 만드는 것이 아니다.**

| 출처 | 비율 | 설명 |
|------|------|------|
| 초기 시드 데이터 (공공 API, 크롤링) | 60~80% | 식약처 데이터, 바코드 DB 등 |
| 업체 등록 (B2B) | 10~20% | 식품 제조사/편의점 등 |
| 사용자 직접 등록 | 5~15% | 커스텀 제품, 미등록 식품 |

따라서 **Product 100만건은 DAU와 직접 비례하지 않으며**, 서비스 성숙도와 데이터 수급 전략에 따라 달라진다.

### Review 데이터 특성

리뷰는 **사용자 행동의 직접적 산출물**이므로 DAU 추정의 핵심 지표이다.

```
리뷰 작성률 = DAU 중 리뷰를 작성하는 비율
- 일반적인 앱: 1~5% (대부분 소비만 함)
- 음식 기록 앱 특성: 5~15% (기록 행위 자체가 핵심 기능)
- Nutri-Diary 특성: 리뷰 = 식단 평가이므로 10~20%로 높게 추정
```

## 2. 서비스 런칭 기간별 시나리오 분석

### 시나리오 A: 런칭 6개월 (빠른 성장기)

```
운영 기간: ~180일
리뷰 1,000만건 / 180일 = 일 평균 ~55,556건 리뷰 생성
```

| 지표 | 보수적 (리뷰율 20%) | 현실적 (리뷰율 12%) | 공격적 (리뷰율 7%) |
|------|-------------------|--------------------|-------------------|
| **필요 DAU** | **~278,000명** | **~463,000명** | **~794,000명** |
| 인당 일 리뷰 수 | 1.0건 | 1.0건 | 1.0건 |
| MAU (DAU×3) | ~834K | ~1.39M | ~2.38M |
| 총 가입자 (MAU×3) | ~2.5M | ~4.2M | ~7.1M |

> **판단:** 6개월 만에 리뷰 1,000만건은 **매우 공격적인 성장**이다. 배달의민족, 마켓컬리 수준의 마케팅 투자가 필요하다. Product 100만건도 6개월 내 확보하려면 대규모 시드 데이터 파트너십이 필수이다.

### 시나리오 B: 런칭 1년 (안정 성장기) — 가장 현실적

```
운영 기간: ~365일
리뷰 1,000만건 / 365일 = 일 평균 ~27,397건 리뷰 생성
(단, 초기에는 적고 후반에 많으므로 가중 적용)
```

**성장 곡선 적용 (S-curve):**

```
월별 리뷰 생성량 추정:
Month  1:    50,000건  (초기)       → DAU ~1,500
Month  2:   100,000건               → DAU ~3,000
Month  3:   200,000건               → DAU ~6,000
Month  4:   400,000건               → DAU ~12,000
Month  5:   600,000건               → DAU ~18,000
Month  6:   800,000건  (성장 가속)   → DAU ~25,000
Month  7: 1,000,000건               → DAU ~30,000
Month  8: 1,200,000건               → DAU ~35,000
Month  9: 1,500,000건               → DAU ~45,000
Month 10: 1,500,000건  (안정화)      → DAU ~45,000
Month 11: 1,500,000건               → DAU ~45,000
Month 12: 1,150,000건               → DAU ~45,000
──────────────────────────────────────────────────
합계:     10,000,000건
```

| 지표 | 값 |
|------|-----|
| **런칭 초기 DAU** | **~1,500명** |
| **6개월 차 DAU** | **~25,000명** |
| **12개월 차 DAU** | **~45,000명** |
| 피크 MAU | ~135,000명 |
| 총 누적 가입자 | ~400,000~500,000명 |
| 인당 일 리뷰 | 1.0~1.2건 |
| 리뷰 작성 참여율 | 12~15% |

> **판단:** 1년 시나리오가 **가장 현실적**이다. 한국 시장에서 건강/다이어트 앱 중 성공적인 사례(예: 다이어트신, 팻시크릿)와 유사한 궤적이다.

### 시나리오 C: 런칭 2년 (성숙기)

```
운영 기간: ~730일
리뷰 1,000만건 / 730일 = 일 평균 ~13,699건
```

```
Phase 1 (Month 1~6):   씨앗 단계
  월 평균 리뷰: 100,000건 → DAU ~3,000
```

## 3. Product 100만건 달성 경로

Product 데이터는 DAU와 다른 축으로 분석해야 한다.

```
                       6개월     1년      2년      3년
─────────────────────────────────────────────────────────
시드 데이터 (공공DB)    500K     500K     500K     500K
크롤링/파트너십         200K     300K     350K     370K
업체 등록              50K      100K     100K     80K
사용자 등록            50K      100K     50K      50K
─────────────────────────────────────────────────────────
합계                   800K     1,000K   1,000K   1,000K
```

**핵심 인사이트:** Product 100만건을 달성하려면:
- 식약처 식품영양성분 DB: ~약 6만건
- 바코드 DB (한국식품안전관리인증원): ~약 30만건
- 해외 DB (USDA, Open Food Facts): ~약 80만건
- **크롤링/제휴 없이 순수 사용자 등록만으로는 불가능**

## 5. 현재 인프라와의 매핑

현재 설정(Tomcat 60 threads, HikariCP 40)과 매핑하면:

| 시나리오 | DAU | 피크 RPS | 현재 인프라 충분? | 병목 지점 |
|---------|-----|---------|-----------------|----------|
| 3년 운영 (12K DAU) | 12,000 | ~15 RPS | **충분** | 없음 |
| 2년 운영 (18K DAU) | 18,000 | ~25 RPS | **충분** | ES→MySQL N+1 쿼리 |
| 1년 성장 (45K DAU) | 45,000 | ~70 RPS | **부족** | 스레드 풀, DB 커넥션, 캐시 필요 |
| 6개월 폭발 (300K+) | 300,000+ | ~500 RPS | **전면 재설계** | 모든 것 |

**결론:** Review 1,000만건 + Product 100만건은 **런칭 1~2년 차, DAU 15,000~45,000명** 규모의 서비스에서 가장 자연스러운 수치이다. 현재 인프라는 DAU ~20,000명까지는 대응 가능하며, 그 이상은 캐싱 레이어와 수평 확장이 필요하다.
